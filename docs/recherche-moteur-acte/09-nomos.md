# Nomos : langage de règles avec extraction assistée par LLM

État examiné : dépôt [`sboghossian/nomos`](https://github.com/sboghossian/nomos) à la révision [`209d4f023cbe406a8e54d787d7046ded61b25b02`](https://github.com/sboghossian/nomos/commit/209d4f023cbe406a8e54d787d7046ded61b25b02), datée du 21 avril 2026. Le README se présente comme un langage expérimental de règles, version 0.1.0, avec AST typé, évaluateur, pont LLM et résolution de citations. C’est une piste pour étudier une syntaxe compacte et l’explicitation des conflits, pas un moteur juridique prêt à l’emploi.

## Ce que le code fait

L’AST de [`packages/core/src/ast.ts`](https://github.com/sboghossian/nomos/blob/209d4f023cbe406a8e54d787d7046ded61b25b02/packages/core/src/ast.ts) conserve règles, conditions, exceptions, priorité, `defeats`, juridiction, date de début `from` et références d’autorité. Une référence peut porter source, type de citation, statut primaire, date, forme canonique et données supplémentaires. Le nœud `ExtractExpr` stocke `verifiedByHuman` et un seuil de confiance : le langage sait représenter ces métadonnées, mais cela ne prouve pas qu’une validation humaine soit imposée à l’exécution.

L’évaluateur [`packages/core/src/evaluator.ts`](https://github.com/sboghossian/nomos/blob/209d4f023cbe406a8e54d787d7046ded61b25b02/packages/core/src/evaluator.ts) calcule la règle ciblée et ses règles directement déclarées comme la défaisant. Si plusieurs règles s’appliquent, le code départage dans cet ordre : priorité numérique, spécificité structurelle, date `from` la plus récente, puis ordre de déclaration (la dernière gagne). La spécificité est une heuristique fondée sur le nombre de `requires`, un bonus si `when` existe et le nombre de `defeats`; ce n’est pas une analyse de domaine juridique. Les commentaires README évoquent lex specialis, mais le code de [`checker.ts`](https://github.com/sboghossian/nomos/blob/209d4f023cbe406a8e54d787d7046ded61b25b02/packages/core/src/checker.ts) précise que la juridiction et la validité temporelle ne sont pas encore vérifiées. Le moteur ne fait qu’ignorer une règle si la date de requête précède `from`; pas de date de fin, ni comparaison de juridictions.

Une trace accompagne le résultat : règles candidates, conditions, valeurs des opérandes, autorités, règles gagnantes ou battues et critère de départage. Cette explication aide à auditer le calcul, mais une référence canonique dans la trace ne démontre pas que son contenu soutient la proposition. Le résolveur de [`packages/citations/src/index.ts`](https://github.com/sboghossian/nomos/blob/209d4f023cbe406a8e54d787d7046ded61b25b02/packages/citations/src/index.ts) reconnaît certains formats de citation américains avec Eyecite. Pour les autres éditeurs — donc les références françaises — il retourne une référence non résolue : il n’extrait ni ne vérifie le texte cité, sa version ou son applicabilité.

## Extraction LLM et inconnues : écarts avec les promesses

Le pont [`packages/llm/src/openrouter.ts`](https://github.com/sboghossian/nomos/blob/209d4f023cbe406a8e54d787d7046ded61b25b02/packages/llm/src/openrouter.ts) envoie à un modèle une demande d’extraction structurée en JSON Schema. Le prompt lui demande d’inférer ce qui serait juridiquement raisonnable si l’information manque, avec une confiance moindre. Cette confiance est déclarée par le modèle, pas calibrée par une validation juridique indépendante. [`resolve.ts`](https://github.com/sboghossian/nomos/blob/209d4f023cbe406a8e54d787d7046ded61b25b02/packages/llm/src/resolve.ts) calcule si un seuil est franchi et conserve cette métadonnée. Dans la CLI [`bin.ts`](https://github.com/sboghossian/nomos/blob/209d4f023cbe406a8e54d787d7046ded61b25b02/packages/cli/src/bin.ts), une confiance sous seuil déclenche un avertissement, mais la valeur est quand même injectée puis évaluée. `verified_by human` ne bloque donc pas réellement le calcul et aucune file de validation humaine n’est implémentée à cette révision. L’ensemble multi-modèles de [`ensemble.ts`](https://github.com/sboghossian/nomos/blob/209d4f023cbe406a8e54d787d7046ded61b25b02/packages/llm/src/ensemble.ts) calcule accord ou désaccord par vote, mais le chemin normal de résolution appelle un seul modèle.

Les verdicts de règles sont booléens. Un identifiant absent devient `null` et échoue dans un test de vérité ; sa négation devient vraie au lieu de rester inconnue (`isTruthy`, `UnaryExpr`). Les comparaisons numériques sans opérandes numériques échouent également. Le système ne propage donc pas un état inconnu à travers ces opérations. Il ne préserve pas un état de conclusion « inconnu », contrairement à la logique vrai / faux / inconnu de PieceMaker ; les liens probatoires de contradiction sont encore une autre information. C’est un risque central pour l’acte : absence d’extraction ne doit pas se transformer en constat contraire.

## Intérêt incrémental pour PieceMaker

PieceMaker exécute déjà ses termes déclaratifs avec un interpréteur (`server/modules/piecemaker-reasoning/engine.ts`), conserve la logique à trois valeurs, les dépendances, les bascules dues aux inconnues et relie les sources aux pièces et aux sections d’acte. La confrontation de deux modèles reste une exploration, pas une fonction réalisée. Nomos pourrait inspirer une représentation compacte de règles défaisables, des priorités explicites et une trace locale des règles candidates et des départages. Sa capacité de lecture de sources et de citations exactes ne doit pas être surévaluée : les citations restent surtout des références, et le contrôle d’applicabilité juridictionnelle/temporelle n’est pas effectif. Une extraction LLM devrait rester une proposition de fait à vérifier, jamais alimenter directement une conclusion juridique comme si elle était établie.

## Maturité, licence et protocole fictif

Le README qualifie le projet d’expérimental et annonce 26 tests à cette révision; l’arbre inclut notamment [`evaluator.test.ts`](https://github.com/sboghossian/nomos/blob/209d4f023cbe406a8e54d787d7046ded61b25b02/packages/core/test/evaluator.test.ts) et le fixture de départage [`tiebreaker.nomos`](https://github.com/sboghossian/nomos/blob/209d4f023cbe406a8e54d787d7046ded61b25b02/packages/core/test/fixtures/tiebreaker.nomos). Il s’agit d’un prototype récent, à historique court; ces tests vérifient des comportements logiciels, pas une pratique juridique. Le fichier [`LICENSE`](https://github.com/sboghossian/nomos/blob/209d4f023cbe406a8e54d787d7046ded61b25b02/LICENSE) contient la licence Apache 2.0, bien que l’API GitHub renvoie `NOASSERTION` pour le champ licence : signaler la divergence de métadonnées, sans conclure que le dépôt n’a pas de licence.

Protocole proposé, non exécuté : créer deux règles fictives, `admissible` si `formulaire_reçu`, et `inadmissible` qui défait la première si `fraude_établie`, avec une autorité fictive « Source A, version 1 ». Tester successivement fait vrai, fait faux et fait absent; l’absence devrait être examinée car Nomos la rabat sur faux. Ajouter deux règles contradictoires de même priorité, puis modifier leur ordre de déclaration afin d’observer le dernier départage; changer `from` et la date de requête; enfin fournir une juridiction incompatible et une extraction sous le seuil. Vérifier dans chaque trace quelles règles ont gagné, si la CLI poursuit malgré l’avertissement, et si l’autorité n’est qu’une référence non résolue. Comparer aux mêmes propositions, états inconnus, liens de source et bascules dans PieceMaker; ne pas interpréter ce test jouet comme une validation du droit ni du produit.
