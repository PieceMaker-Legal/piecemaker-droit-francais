# Accord Project pour le moteur d’acte de PieceMaker

État vérifié le 24 octobre 2026 à partir des dépôts publics Accord Project. « Constat » désigne ce que documentent les sources du projet ; « inférence » désigne l’évaluation pour PieceMaker. Le contexte retenu est celui fourni pour cette étude : acte représenté par un objet JavaScript déclaratif, non exécuté, avec termes `si`, `sauf`, `l_une`, logique à trois valeurs, sources datées et exactes, preuves, hypothèses et calculs ; sections `id`/`intitule`/`traite`/`texte`, impression DOCX et fusion à trois voies des retouches.

## État des projets

**Constat.** [`markdown-transform`](https://github.com/accordproject/markdown-transform) est un dépôt TypeScript Apache-2.0, actif et organisé en modules npm. Son README cartographie notamment `packages/markdown-common` (Markdown ↔ DOM CommonMark), `packages/markdown-cicero` (CommonMark ↔ CiceroMark), `packages/markdown-template` (texte et données ↔ TemplateMark) et `packages/markdown-html` (CiceroMark → HTML). Les schémas TemplateMark et CiceroMark sont eux-mêmes décrits en Concerto. Le DOM de TemplateMark comporte des nœuds nommés `ConditionalDefinition`, `OptionalDefinition`, `WithDefinition`, `JoinDefinition`, `FormulaDefinition` et des nœuds de variables. Le dépôt se présente donc comme un parseur/transformation de formats documentaires, pas comme un moteur général de raisonnement juridique.

**Constat.** L’URL historique [`accordproject/cicero`](https://github.com/accordproject/cicero) redirige aujourd’hui vers [`template-archive`](https://github.com/accordproject/template-archive), dépôt public Apache-2.0 qui reste actif. Son README décrit les gabarits de clauses en langue naturelle liés à un modèle de données : Cicero génère un parseur pour extraire et valider des données depuis le texte, puis permet d’exécuter une clause depuis un objet JSON. Le dépôt conserve des paquets tels que `cicero-cli` et `cicero-core`, et sert de suite historique de Cicero. La documentation actuelle oriente toutefois les nouveaux usages vers `markdown-transform` et `template-engine` ; « Cicero » désigne aussi encore des formats et des nœuds (`CiceroMark`). Il faut donc distinguer le nom du dépôt/produit historique des composants plus récents.

**Constat.** [`concerto`](https://github.com/accordproject/concerto) est le langage de schéma et runtime de données, Apache-2.0, également actif. Le README liste `packages/concerto-cto` pour l’analyse syntaxique, `packages/concerto-core` pour la gestion des modèles, la validation et la sérialisation, et `packages/concerto-analysis` pour comparer des versions de modèles. Il génère des types et schémas vers plusieurs langages/formats. C’est une base mûre pour contraindre des données métier et produire des erreurs de structure/types, mais pas un modèle de preuve ou de provenance.

## Logique : TypeScript ou Ergo

**Constat.** Le dépôt actuel [`template-engine`](https://github.com/accordproject/template-engine) est un moteur TypeScript. Son pipeline documenté valide le TemplateMark et les données contre Concerto, compile les expressions TypeScript incorporées, les évalue, construit un AgreementMark puis valide la sortie. `src/` contient l’implémentation ; le README nomme `TemplateMarkToJavaScriptCompiler` et `JavaScriptEvaluator`. Le moteur annonce une évaluation directe ou dans un processus Node isolé ; l’exécution directe de logique non fiable est expressément risquée. Le moteur demande Node ≥ 22. L’Apache-2.0 s’applique au code source ; la documentation Accord Project est publiée sous CC-BY-4.0.

**Constat.** [`Ergo`](https://github.com/accordproject/ergo) est un autre langage, dont le dépôt dit que le compilateur est construit avec Coq, avec parsing et outils en OCaml et génération/type-checking s’appuyant sur Q*cert. Le README qualifie langage et compilateur de « early development ». Ergo produit du JavaScript exécutable pour des contrats à clauses, requêtes, réponses et état ; ce n’est pas le langage de logique du nouveau moteur TemplateMark, qui documente TypeScript.

**Inférence.** Ni TypeScript embarqué ni Ergo ne convient à la règle actuelle « objet JS déclaratif, jamais exécuté » : ce serait inverser une propriété de sécurité et d’auditabilité de PieceMaker. Concerto peut toutefois fournir un motif pour typer et valider les données d’entrée/sortie. Si les actes restent du JSON/JS, un validateur étroit sur le schéma existant paraît plus incrémental que d’introduire un langage ou un runtime supplémentaires.

## Apports possibles et limites concrètes

**Inférence — apport incrémental réel : AST documentaire typé et validation de forme.** TemplateMark montre un AST de document enrichi avec des catégories explicites de nœuds, et Concerto apporte une définition de schéma, validation et sérialisation. PieceMaker pourrait emprunter ces idées pour formaliser la structure des sections et les variantes de `traite` sans copier leur sémantique. Les sections `id`/`intitule`/`traite`/`texte` et les expressions `si`/`sauf`/`l_une` sont propres au produit : ni le DOM Accord Project ni Concerto n’encode les preuves, les hypothèses, la date/version d’une source, les citations exactes ou la sémantique « inconnu » de la logique à trois valeurs. Ces champs exigeraient un modèle PieceMaker dédié, avec validation des références et des invariants.

**Inférence — modèle de prose et transformation.** TemplateMark illustre une séparation utile entre texte, variables, blocs conditionnels et données. `markdown-transform` sépare le parseur du document de ses transformations, et sait convertir des formats CommonMark/CiceroMark ; le moteur transforme TemplateMark JSON en AgreementMark JSON. Cela peut inspirer un modèle de nœuds révisable avant impression et un pipeline qui garde l’acte structuré en source de vérité. Mais les conditions TemplateMark sont des expressions TS qui calculent si le texte s’affiche ; elles ne représentent ni la justification juridique d’une proposition ni l’incertitude sur la preuve. Le DOM est aussi centré sur le gabarit et le rendu, tandis que PieceMaker lie les affirmations à un dossier évolutif.

**Limite DOCX.** Les projets annoncent DOCX comme format de sortie parmi HTML/PDF/DOCX, via `markdown-transform`/`template-cli`. Les sources consultées ne décrivent pas de round-trip DOCX sans perte, de conservation des identifiants de sections lors d’allers-retours, ni de fusion éditoriale à trois voies avec gestion des conflits. La conversion vers un format imprimable n’implique pas ces capacités. Par inférence, Accord Project peut aider à générer l’impression depuis l’acte structuré, mais ne remplace pas l’éditeur DOCX ni le mécanisme de rapprochement des retouches de PieceMaker.

**Conclusion d’étude.** Le réemploi le plus défendable est conceptuel et local : emprunter à Concerto les idées de schéma explicite/validation, et à TemplateMark la séparation texte/AST/transformation. Ne pas adopter son exécution TypeScript ni Ergo pour le moteur de raisonnement, et ne pas compter sur ces dépôts pour la preuve juridique, le vrai round-trip Word ou la fusion trois voies. Les sources de code/documentation sont majoritairement Apache-2.0 ; documentations sous CC-BY-4.0. Avant de copier du code, vérifier la licence du paquet exact et ses dépendances : cette note n’évalue pas la compatibilité de chaque transitif.
