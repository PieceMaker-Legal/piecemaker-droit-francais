# L4 (Legalese) : apports ciblés pour PieceMaker

Analyse statique au commit [`b085e304d72fb7b965b8bc63a5f4b913f9bb3eed`](https://github.com/legalese/l4-ide/tree/b085e304d72fb7b965b8bc63a5f4b913f9bb3eed). L’ancien dépôt `smucclaw/l4-ide` renvoie vers celui continué par Legalese. Le fichier [`LICENSE`](https://github.com/legalese/l4-ide/blob/b085e304d72fb7b965b8bc63a5f4b913f9bb3eed/LICENSE) indique Apache-2.0, malgré les métadonnées GitHub `NOASSERTION`. Aucun code n’a été installé ni exécuté.

PieceMaker conserve un objet JavaScript déclaratif non exécuté pour un acte : sections structurées, conditions à trois valeurs, sources datées, preuves, hypothèses et calculs, impression DOCX et fusion des retouches à trois voies. L4 est un langage fonctionnel exécutable pour règles, contrats et législation, avec compilateur Haskell et certains clients TypeScript. Il ne remplace pas directement le format d’acte PieceMaker.

## Ce qui est livré dans le dépôt

**Constat.** Le README énumère les paquets Haskell `jl4-core` (parseur, vérificateur de types, évaluateur), `jl4` (CLI et génération JSON Schema), `jl4-lsp`, `jl4-repl`, `jl4-service` (évaluation REST), `jl4-websessions`, `jl4-query-plan`, `jl4-actus-analyzer`, `jl4-wasm` et `jl4-mlir`. Dans l’arbre GitHub à ce SHA, les dossiers `jl4-core`, `jl4-repl`, `jl4-service`, `jl4-query-plan`, `jl4-wasm` et `jl4-mlir` existent, mais pas `jl4-actus-analyzer`, pourtant annoncé. Les clients TypeScript incluent l’extension VS Code, l’éditeur web et des bibliothèques partagées. Analyse statique, sans compilation ni exécution.

La documentation de la même révision montre des fonctions effectivement raccordées : le REPL expose `:decides`, `:queryplan` et `:trace`; la documentation du service décrit des routes `query-plan`; les traces peuvent être rendues en GraphViz. Le vérificateur de types signale les branches manquantes ou redondantes pour les `CONSIDER` sur des types algébriques finis. À la révision consultée, la vérification est limitée : `BOOLEAN` et les énumérations sont exhaustifs, mais les valeurs `NUMBER`, `STRING` et `DATE` ne sont pas énumérables et les conteneurs `MAYBE`, `EITHER`, `LIST` ne sont pas encore couverts. Ces limites sont spécifiées dans [`doc/concepts/type-system/exhaustiveness.md`](https://github.com/legalese/l4-ide/blob/b085e304d72fb7b965b8bc63a5f4b913f9bb3eed/doc/concepts/type-system/exhaustiveness.md).

Le code ACTUS effectivement présent est une bibliothèque L4 dans [`jl4-core/libraries/`](https://github.com/legalese/l4-ide/tree/b085e304d72fb7b965b8bc63a5f4b913f9bb3eed/jl4-core/libraries), documentée dans [`doc/reference/libraries/actus.md`](https://github.com/legalese/l4-ide/blob/b085e304d72fb7b965b8bc63a5f4b913f9bb3eed/doc/reference/libraries/actus.md) et accompagnée de tests dorés. Elle couvre des types, événements, calculs de jours, échéanciers et fonctions d’évaluation ACTUS ; ce n’est pas le paquet d’analyseur ACTUS/FIBO annoncé par le README. La passerelle générale ACTUS–L4 est un cahier des charges dans [`specs/todo/ACTUS-L4-BRIDGE-SPEC.md`](https://github.com/legalese/l4-ide/blob/b085e304d72fb7b965b8bc63a5f4b913f9bb3eed/specs/todo/ACTUS-L4-BRIDGE-SPEC.md), donc encore au stade de spécification dans cet arbre. Par ailleurs, `WITHIN` est un délai relatif sur une ligne de temps numérique ; la référence n’a ni date absolue de type « avant le 1er janvier » ni ancrage à un événement nommé hors chaînage. Elle recommande de composer les obligations via `HENCE` pour compter depuis l’événement précédent ([`doc/reference/regulative/consequences.md`](https://github.com/legalese/l4-ide/blob/b085e304d72fb7b965b8bc63a5f4b913f9bb3eed/doc/reference/regulative/consequences.md)).

## Apports possibles, sans migration de moteur

**Types adaptés aux catégories juridiques.** L4 sépare au niveau des types les règles constitutives (définir/classer/calculer une valeur) et les règles régulatives (partie, devoir, délai et conséquences). Les premières retournent une valeur ; les secondes un `DEONTIC` qui peut être rempli, enfreint ou encore pendant. Cette distinction, décrite dans [`constitutive-vs-regulative.md`](https://github.com/legalese/l4-ide/blob/b085e304d72fb7b965b8bc63a5f4b913f9bb3eed/doc/concepts/legal-modeling/constitutive-vs-regulative.md), rappelle un contrôle de conception utile : ne pas confondre qualification juridique et obligation de faire. Pour PieceMaker, l’inspiration incrémentale serait de valider les catégories déjà dans l’objet (affirmation, preuve, hypothèse, calcul, obligation mentionnée dans l’acte) sans introduire des objets ou une sémantique L4.

**Situations, obligations et délais.** L4 modélise explicitement `PARTY`, `MUST`/`MAY`/`SHANT`, `WITHIN`, `HENCE` et `LEST`. À partir d’un instant de départ et d’événements datés (partie, action, heure), l’évaluation retourne `FULFILLED`, `BREACH` ou l’obligation résiduelle à reprendre plus tard. Les conséquences et réparations peuvent s’enchaîner. Cela dépasse un prédicat vrai/faux et évite de traiter une absence d’événement avant échéance comme une violation. **Inférence :** cette représentation peut éclairer une future vue PieceMaker de suivi d’obligations dans le temps, si le besoin existe. Pour le moteur actuel de rédaction d’actes, elle serait une couche métier séparée ; les échéances procédurales à date fixe ne s’intègrent pas directement puisque la primitive documentée est un `WITHIN` relatif.

**Plans de questions.** Le README et l’API documentent un plan de requête qui renvoie les entrées encore nécessaires, classées selon leur impact sur la décision, ainsi que des commandes REPL. L’intérêt PieceMaker serait d’ordonner les questions de collecte de faits selon leur capacité à changer la conclusion ou le calcul, au lieu d’interroger tout le dossier uniformément. Cette capacité n’apporte pas en elle-même une preuve : l’interface devrait relier chaque réponse à la pièce, à la date et à l’extrait exacts, ce qui reste une intégration PieceMaker.

**Explications et contrôles statiques.** L4 annonce une trace de la question principale jusqu’à la condition déterminante, avec visualisation de graphe, et un contrôle d’exhaustivité pour les énumérations. PieceMaker peut retenir l’idée de produire une explication lisible par règle : valeurs des conditions, branche retenue, calcul intermédiaire, justification, et référence de source. L’exhaustivité est pertinente pour les catégories fermées déjà utilisées par l’interface (p. ex. état ou type de traitement), non pour des conditions `si` qui sont des conjonctions. Elle ne remplace pas la logique à trois valeurs de PieceMaker ni la vérification de complétude de toutes les pièces.

Le module de devise documenté (`IMPORT currency`) stocke des montants en unités mineures entières, valide un code ISO 4217 et documente arrondis et opérations. Il offre un exemple utile pour éviter les erreurs de flottants et distinguer monnaie/devises lors d’un calcul. Cela ne justifie pas d’importer le runtime : PieceMaker peut encoder ces contraintes dans son propre schéma et moteur déjà existant.

## Conclusion

L4 vaut surtout comme référence pour modéliser séparément qualifications et obligations, calculer des devoirs dans le temps, poser les questions décisives et expliquer une décision par traces. L’arbre confirme un moteur de règles, un module de plans de questions et une bibliothèque ACTUS, mais pas le paquet `jl4-actus-analyzer` pourtant annoncé dans le README ; la passerelle ACTUS est encore une spécification `todo`. Les autres limites documentées incluent l’exhaustivité partielle et les délais uniquement relatifs. Le réemploi utile pour PieceMaker est un petit ensemble d’invariants, de types métier, de cas tests et d’explications autour de l’objet actuel. Adopter le langage, le compilateur Haskell ou son runtime transformerait le choix de représentation et sortirait du besoin incrémental étudié.
